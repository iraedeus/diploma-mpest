# Спецификация системы сбора, хранения и анализа требований к библиотекам анализа смесей распределений

Документ регламентирует архитектуру, схему хранения и методику формирования требований к библиотеке `pysatl-mpest` в рамках выпускной квалификационной работы:
**«Развитие и подготовка к выпуску библиотеки pysatl-mpest для анализа смесей вероятностных распределений»**.

---

## 1. Контекст и решаемая проблема

При проведении сравнительного анализа существующих открытых инструментов по смесям распределений возникает конфликт между полнотой анализа и его читаемостью:
* Полноразмерная сводная матрица (>10–15 инструментов на >40 функциональных требований) в чистом Markdown-документе занимает свыше 15 колонок, не помещается на стандартных дисплеях, провоцирует постоянные мердж-конфликты в Git и не позволяет динамически фильтровать данные.
* Постулирование требований «сверху вниз» (до анализа инструментов) приводит к субъективному списку и потере уникальных архитектурных решений существующих библиотек.
* Для научного обоснования в ВКР критически важно связывать каждое функциональное требование с доказательной базой: **в каких статьях оно исследовано, сколько всего статей его подтверждают и каковы их показатели цитируемости**.

**Решение:** Разделение уровней **хранения** (машиночитаемые версионируемые CSV), **генерации** (Python-скрипт фильтрации и формирования срезов) и **представления** (читаемые тематические таблицы строго в формате Markdown с привязкой статей и цитирований).

```
┌────────────────────────────────────────────────────────────────────────────────────────┐

│ 1. ХРАНИЛИЩЕ (Данные)   │ 2. ОБРАБОТКА (Генератор)      │ 3. ПРЕДСТАВЛЕНИЕ (Дашборд/MD)│
```

## 2. Схема и структура хранения данных (CSV Data Model)

Все первичные факты хранятся в нормализованном табличном виде в формате CSV (UTF-8, разделитель запятая `,`).

### 2.1. Каталог инструментов (`tools.csv`)
Содержит реестр исследуемых открытых библиотек и пакетов:

| Поле | Тип | Описание | Пример |
|:---|:---|:---|:---|
| `tool_id` | `str` (PK) | Уникальный буквенно-цифровой идентификатор | `mclust`, `pomegranate`, `mixR` |
| `name` | `str` | Официальное название инструмента / пакета | `mclust 5`, `Pomegranate` |
| `ecosystem` | `str` | Языковая среда / экосистема | `Python`, `R`, `Julia`, `C++` |
| `repository_url` | `str` | Ссылка на репозиторий (GitHub, GitLab, CRAN) | `https://github.com/cran/mclust` |
| `license` | `str` | Тип лицензии исходного кода | `GPL-2`, `MIT`, `BSD-3-Clause` |
| `paper_reference`| `str` | Ссылка на научную публикацию / DOI (если есть) | `10.32614/rj-2016-021` |
| `status` | `str` | Статус анализа: `candidate`, `in_review`, `reviewed` | `reviewed` |
| `description` | `str` | Краткое назначение и ключевая специфика | `Gaussian mixture models & clustering` |

### 2.2. Каталог требований и возможностей (`requirements.csv`)
Содержит реестр атомарных требований, извлеченных из анализа инструментов и проекта `pysatl-mpest`:

| Поле | Тип | Описание | Пример |
|:---|:---|:---|:---|
| `req_id` | `str` (PK) | Уникальный код требования с префиксом типа | `EST-01`, `INIT-03`, `STRUC-02` |
| `type` | `str` | Тип требования (см. раздел 3) | `estimation`, `initialization`, `structure`, `technical`, `infrastructure` |
| `name` | `str` | Краткое наименование функциональной возможности | `ECME-алгоритм (ODL-шаги)` |
| `description` | `str` | Детальное описание и математический смысл | `Обновление параметров через суррогат Q либо напрямую через L_obs` |
| `discovered_in` | `str` | Инструмент или источник, из которого извлечено | `Liu & Rubin (1994), Bee (2026)` |
| `priority` | `str` | Приоритет для релиза: `must`, `should`, `could` | `must` |

### 2.3. Матрица оценок инструментов (`evaluations.csv`)
Связывает инструменты и требования с обязательным подтверждением (пруфлинком на код или документацию):

| Поле | Тип | Описание | Пример |
|:---|:---|:---|:---|
| `tool_id` | `str` (FK) | Идентификатор инструмента из `tools.csv` | `mixR` |
| `req_id` | `str` (FK) | Идентификатор требования из `requirements.csv` | `STRUC-03` |
| `status` | `str` | Наличие возможности: `yes`, `partial`, `no` | `yes` |
| `evidence_note` | `str` | Пояснение реализации или причины ограничения | `Поддерживает Weibull, Gamma через Newton-Raphson` |
| `evidence_link` | `str` | Ссылка на строку кода / раздел документации | `R/mix_weibull.R#L45` |

### 2.4. Реестр научных статей с показателями цитируемости (`articles.csv`)
Интегрируется с каталогом литературы ВКР (OpenAlex / CrossRef / Google Scholar) и хранит научные метрики:

| Поле | Тип | Описание | Пример |
|:---|:---|:---|:---|
| `article_id` | `str` (PK) | Идентификатор публикации в реестре | `P0001`, `P0016`, `P0183` |
| `title` | `str` | Полное название публикации | `Maximum Likelihood from Incomplete Data via the EM Algorithm` |
| `authors` | `str` | Авторы публикации | `Dempster A. P., Laird N. M., Rubin D. B.` |
| `year` | `int` | Год публикации | `1977` |
| `citations_count`| `int` | Количество цитирований (метрика авторитетности) | `65420` |
| `doi` | `str` | Цифровой идентификатор DOI | `10.1111/j.2517-6161.1977.tb01600.x` |
| `url` | `str` | Ссылка на полный текст / издательство | `https://doi.org/10.1111/...` |

### 2.5. Связующая таблица «Требование — Научные статьи» (`requirement_articles.csv`)
Определяет доказательную научную базу для каждого функционального требования:

| Поле | Тип | Описание | Пример |
|:---|:---|:---|:---|
| `req_id` | `str` (FK) | Идентификатор требования из `requirements.csv` | `EST-03` |
| `article_id` | `str` (FK) | Идентификатор публикации из `articles.csv` | `P0402` (Liu & Rubin, 1994) |
| `role` | `str` | Роль статьи по отношению к требованию: `foundation`, `method`, `benchmark` | `foundation` |
| `context_note` | `str` | Конкретное место/формула в статье, обосновывающее фичу | `Введен ODL-шаг и доказана монотонная сходимость (разд. 2, теорема 1)` |

## 3. Таксономия и классификация требований

Все функциональные возможности классифицируются по строго определенным категориям:

### 3.1. Тип: Оценивание параметров (`estimation`)
Алгоритмы оптимизации и методы вычисления оценок параметров смеси:
* **Классы алгоритмов:** Классический EM (одновременный M-шаг), ECM (условная максимизация по блокам $Q$), ECME (условные шаги по $Q$ либо по наблюдаемому лог-правдоподобию всей смеси ODL), GEM (Generalized EM с частичным улучшением), прямая численная оптимизация (Direct Numerical MLE через L-BFGS-B, Nelder-Mead, Powell), метод моментов (MoM / L-моменты).
* **Управление параметрами:** Фиксация подмножеств параметров компонентов (`view(**fixed_params)` — например, фиксация сдвига при оценке масштаба), явные параметрические границы (bounds, constraints), симплекс весов ($\sum \alpha_k = 1, \alpha_k \ge 0$).
* **Численная стабильность:** Защита от сингулярностей (схлопывание дисперсии $\sigma_k \to 0$, $L \to \infty$), квазиньютоновское ускорение EM (SQUAREM), трассировка сходимости и логирование истории итераций.

### 3.2. Тип: Инициализация (`initialization`)
Стратегии формирования начальных приближений параметров и весов смеси:
* **Пользовательская инициализация:** Ручное задание начальной смеси с проверкой принадлежности носителям и границам.
* **Рандомизированный мультистарт:** Генерация возмущенных начальных приближений и выбор лучшей сходимости.
* **Квантильное разбиение:** Детерминированное разрезание вариационного ряда выборки на равные интервалы/квантили.
* **Кластеризация данных:** Инициализация центров и масштабов через k-means, иерархическую кластеризацию (HC) или спектральное разбиение.
* **Метод моментов для старта:** Расчет грубых начальных приближений формы и масштаба через эмпирические моменты/квантили.

### 3.3. Тип: Структура смеси (`structure`)
Определение состава, числа и свойств компонент:
* **Тип структуры компонент:** Однородные смеси (все компоненты одного семейства) vs **разнородные (гетерогенные) смеси** (компоненты разных семейств в одной модели, например $\text{Normal} + \text{Weibull}$ или $\text{Lognormal} + \text{Pareto}$).
* **Специфика распределений:** Поддержка положительных асимметричных семейств (Weibull, Gamma, Lognormal), тяжелых хвостов (Pareto, Cauchy), ограниченных компактов (Beta, Uniform), **распределений с неизвестной границей/порогом носителя** ($x \ge x_{\min}$).
* **Выбор порядка смеси ($K$):** Автоматический подбор числа компонент по информационным критериям (AIC, BIC, ICL, CAIC).
* **Статистическая проверка гипотез:** Параметрический бутстреп-LRT (Likelihood Ratio Test) для тестирования гипотезы $H_0: K=k$ против $H_1: K=k+1$.
* **Динамический прунинг:** Автоматическое удаление компонент с вырожденным весом ($\alpha_k < \varepsilon$) во время итераций.
* **Сравнение конфигураций семейств:** Автоматическое ранжирование конкурирующих наборов семейств для одной выборки.

### 3.4. Вспомогательные типы: Архитектура (`technical`) и Инфраструктура (`infrastructure`)
* **Технические:** Модульность пайплайна (свободная замена E- и M-шагов), расширяемость новыми распределениями через открытые интерфейсы (OCP), иммутабельность структур параметров (`Parametrization`), логарифмическая стабильность (`logsumexp`), статическая типизация (`mypy --strict`), фасадная совместимость с `scikit-learn` API.
* **Инфраструктурные:** Пакетный менеджер (Poetry), тестирование (pytest), **property-based тестирование математических инвариантов (Hypothesis)**, покрытие тестами ($\ge 85\%$), линтинг (Ruff), CI/CD (GitHub Actions), документация (Sphinx).

## 4. Протокол извлечения требований «снизу вверх» (Bottom-Up Workflow)

При подключении каждого нового open-source инструмента выполняется следующий регламент:

1. **Регистрация инструмента:** Добавление записи в `tools.csv` (название, репозиторий, лицензия, ссылка на публикацию).
2. **Анализ возможностей по коду и документации:**
   * Проверка поддерживаемых распределений и возможности комбинировать разные семейства в одной модели.
   * Определение используемого алгоритмического аппарата (наличие явных M-шагов, численных оптимизаторов, ODL-шагов, методов инициализации).
   * Изучение интерфейса выбора $K$ (есть ли бутстреп-LRT или только расчет BIC).
3. **Фиксация новых требований:** Если инструмент решает задачу оригинальным способом (например, интервальная оценка по гистограммам в `rebmix` или работа со сгруппированными данными в `mixR`), в `requirements.csv` заносится новое атомарное требование с атрибутом `discovered_in`.
4. **Проставление оценок:** В `evaluations.csv` заносятся строки для данного `tool_id` по каждому требованию со строгим статусом:
   * `yes` — возможность заявлена и подтверждена кодом/тестом.
   * `partial` — возможность работает только для частного случая (напр., только для Гаусса или только с равными дисперсиями).
   * `no` — возможность отсутствует.
   * Обязательно указывается `evidence_note` и `evidence_link`.
5. **Маппинг научных публикаций:** Для каждого подтвержденного требования связываются публикации из `articles.csv` через таблицу `requirement_articles.csv` с фиксацией контекста и цитируемости.

## 5. Спецификация генератора интерактивного дашборда (`generate_dashboard.py`)

Для построения интерактивного представления используется генератор автономного HTML-дашборда.

### 5.1. Интерфейс запуска
```bash
python3 articles/scripts/generate_dashboard.py [--data-dir articles/raw] [--output articles/dashboard.html]
```

Дашборд генерируется в виде единого автономного файла [`articles/dashboard.html`](dashboard.html), открывается в любом браузере и включает в себя:
* Светофорную цветовую индикацию возможностей (зеленый / желтый / красный);
* Полнотекстовый поиск по мере ввода;
* Фильтры по категориям требований и экосистемам инструментов;
* Аналитические пресеты («киллер-фичи `pysatl-mpest`», «бэклог», «высокоцитируемые темы»);
* Модальный просмотр обоснований и ссылок на строки кода;
* Интерактивный slide-over навигатор доказательной литературы с фильтрами по цитированиям и экспорт в Markdown/BibTeX.

3. **Фильтрация требований по научной доказательной базе:**
   * `--min-articles`, `-a <N>`: отображать только требования, подтвержденные **не менее чем $N$ научными статьями** (позволяет отсекать единичные/экзотические идеи и фокусироваться на устойчивых методиках).
   * `--min-citations`, `-c <M>`: учитывать/показывать статьи только с количеством цитирований **$\ge M$** (фильтр высокоцитируемых фундаментальных трудов).

4. **Сортировка и представление статей:**
   * `--sort-by-citations`: сортировать список статей внутри каждого требования **по убыванию числа цитирований** (первыми выводятся классические труды с наибольшим индексом цитирования).
   * `--show-articles`: флаг для вывода подробного списка статей с авторами, годом и числом цитирований (по умолчанию выводится компактный формат вида `N статей: Dempster et al. (1977, cit: 65k), ...`).

5. **Выходной файл:**
   * `--output`, `-o <path>`: путь к выходному Markdown-файлу (если не задан — вывод в stdout).

### 5.2. Требования к верстке Markdown-вывода
Генератор формирует Markdown-отчет, разбитый на компактные таблицы по типам требований (не более 5–8 колонок на таблицу при фильтрации), исключая эффект горизонтального скролла. 

**Пример генерируемой таблицы с наукометрией:**

| Код | Требование / Возможность | `mpest` | `mclust` | `mixR` | Статьи (N) | Ключевые публикации (цитирования) |
|:---|:---|:---:|:---:|:---:|:---:|:---|
| **EST-01** | Классический EM-алгоритм | Есть | Есть | Есть | 5 | Dempster et al. (1977, **65.4k**), Redner & Walker (1984, **1.8k**) |
| **EST-03** | ECME-алгоритм (ODL-шаги) | Есть | Нет | Нет | 2 | Liu & Rubin (1994, **980**), Bee (2026, **12**) |
| **STRUC-07** | Параметрический бутстреп-LRT | Есть | Есть | Есть | 3 | McLachlan (1987, **410**), Scrucca et al. (2016, **850**) |

Благодаря этому автор и научный руководитель сразу видят:
1. Какие требования являются фундаментальными стандартом индустрии (сотни/тысячи цитирований, присутствуют в большинстве инструментов).
2. Какие требования являются передовыми или узкоспециализированными (например, ECME с ODL для пороговых распределений).
